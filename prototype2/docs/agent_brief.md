# 데이터 작성 브리프 (서브에이전트용)

프로젝트: Qwen 3B를 SFT로 학습시켜, 사용자가 대충 쓴 프롬프트를 **역할 명시 · 모호한 지시 명확화 · 구조화 · 출력 형식 명시화**로 개선한 프롬프트로 바꿔 주는 모델을 만든다. 당신은 학습 데이터(입력 → 개선 프롬프트 쌍)를 직접 손으로 작성한다.

작업 폴더: 저장소 루트

## 1. 파일 형식 (`data/raw/<파일명>.txt`, UTF-8)

샘플 하나 = 헤더 1줄 + `>>> INPUT` 블록 + `>>> OUTPUT` 블록. 샘플 사이는 빈 줄 하나.

```
@@@ <id> | <task> | <level> | <domain> | <persona> | <tone>
>>> INPUT
(사용자가 쓴 원본 프롬프트)
>>> OUTPUT
(개선된 프롬프트)
```

- task: 설명, 요약, 기획, 비교, 추천, 기타 / id 접두사: exp, sum, pln, cmp, rec, etc (예: `pln_0001`)
- level: L1(키워드 수준, 정보 거의 없음) / L2(목적·대상 등 일부 정보 있음, 형식·범위 불분명) / L3(이미 구체적 → 원본 정보를 전부 살리고 구조·형식만 보완, 가정 최소)
- domain (12개, 고르게): IT·개발, 교육·학습, 비즈니스·마케팅, 금융·경제, 건강·의료, 여행, 요리·생활, 학술·연구, 법·행정, 문화·엔터, 커리어, 육아·관계
- persona (고르게, 특히 취준생·개발자·교사·자영업자·연구자를 빠뜨리지 말 것): 학생, 직장인, 개발자, 자영업자, 교사, 연구자, 주부, 시니어, 취준생, 프리랜서
- tone(입력의 말투): 반말 30%, 존댓말 40%, 구어체(오타·줄임말) 15%, 영어혼용 15%
- 헤더 값은 위 목록의 철자 그대로(가운뎃점 `·` 포함).

## 2. 출력 템플릿 (섹션 이름·순서 고정)

```
[과제 유형] <task>

[역할]
당신은 ~입니다.  (구체적 직무·경력·관점. "전문가" 같은 일반 표현 금지)

[과제]
(명확해진 핵심 지시 1~2문장)

[맥락 및 가정]
- (원본에 있던 정보는 그대로)
- 가정: (합리적 기본값을 정한 경우)
- (사용자만 알 수 있는 필수 정보): {{설명}}

[원문]                 ← 입력에 원문 텍스트가 붙어 있을 때만. 입력 텍스트를 글자 하나 바꾸지 말고 그대로 복사
...

[수행 단계]
1. ...
2. ...

[출력 형식]
- 형식: (표/번호 목록/문단/체크리스트/타임라인/슬라이드 구성 등)
- 분량: (글자 수, 줄 수, 문장 수, 슬라이드 수 등 구체적으로)
- 톤:
- 반드시 포함:
```

## 3. 절대 규칙

1. 원본 프롬프트에 **답하지 않는다.** OUTPUT은 개선된 프롬프트만. 서두·맺음말("다음은 개선된 프롬프트입니다") 금지. OUTPUT 첫 줄은 반드시 `[과제 유형] <task>`.
2. 원본의 의도·주제·범위를 바꾸지 않는다.
3. 원본에 없는 사실(수치, 고유명사, 사용자 상황)을 단정하지 않는다 → `가정:`으로 표시하거나 `{{...}}` 빈칸. `OOO`, `○○○`, `XXX` 같은 빈칸 표기 금지.
4. 헤더의 persona는 메타데이터일 뿐 모델은 못 본다. OUTPUT은 INPUT 텍스트에서 알 수 있는 정보만 근거로 써야 한다(persona로 추정한 대상은 `가정:`으로).
5. L3는 원본의 모든 조건(분량, 포함 항목, 형식)을 빠짐없이 옮기고, 가정은 거의 추가하지 않는다.
6. `[수행 단계]`는 `1. ` 형식 번호 목록. 단계 수는 2~5개로 다양하게(4개만 반복하지 말 것).
7. `[출력 형식]`에는 `- 형식:`, `- 분량:`, `- 톤:`, `- 반드시 포함:` 네 줄이 반드시 있어야 한다.
8. 역할 문구, 출력 형식(표/목록/문단/체크리스트/타임라인/슬라이드/메일 등), 분량 표현을 다양하게. 같은 표현 반복 금지.
9. 실존 인물·기관에 대한 가짜 뉴스나 허위 사실을 만들지 않는다. 원문이 필요하면 가상의 회사·도시·인물(예: 새솔시, 한빛전자)을 쓴다. 저작권 있는 글(노래 가사, 책 본문)을 원문으로 옮기지 않는다.
10. 같은 입력·주제 중복 금지. 입력 길이·모호도·말투를 실제 사용자처럼 다양하게(L1은 "블록체인 설명해줘"처럼 짧게, 오타·줄임말 섞기).

## 4. task별 필수 명확화 항목

- 설명: 대상 독자 수준, 설명 깊이, 예시·비유 포함 여부
- 요약: 원문(있으면 [원문], 없으면 `{{요약할 텍스트를 여기에 붙여 넣기}}`), 요약 분량, 보존할 핵심 요소(수치·결정사항 등), 요약 형식. 요약은 약 절반이 원문 포함(원문 150~600자 정도로 짧게).
- 기획: 목표, 제약(예산·기간·인원 — 모르면 `{{...}}` 또는 가정), 산출물 구성 항목
- 비교: 비교 대상, 비교 기준(3~6개), 최종 결론/추천 제시 여부, 비교 형식(표 권장)
- 추천: 사용자 조건·선호(모르면 `{{...}}`), 추천 개수, 항목별 추천 근거 형식, 제외 조건
- 기타: 위 5개에 속하지 않는 요청(번역, 이메일·자기소개서 등 글쓰기, 코드 작성, 문장 교정, 브레인스토밍, 분류, 질문 생성 등). `[과제 유형] 기타`로 쓰고 같은 템플릿 적용.

## 5. 예시

```
@@@ exp_0002 | 설명 | L1 | 금융·경제 | 주부 | 존댓말
>>> INPUT
인플레이션이 뭔가요?
>>> OUTPUT
[과제 유형] 설명

[역할]
당신은 경제 뉴스를 쉽게 풀어 주는 생활경제 칼럼니스트입니다.

[과제]
인플레이션의 뜻과 발생 원인, 그리고 일상생활에 미치는 영향을 설명해 주세요.

[맥락 및 가정]
- 가정: 독자는 경제학 지식이 없는 일반 성인입니다.
- 가정: 학술적 이론보다 생활 속 체감 위주의 설명을 원합니다.

[수행 단계]
1. 인플레이션을 쉬운 말로 정의합니다.
2. 주요 원인(수요 증가, 원자재·비용 상승, 통화량 증가)을 각각 짧게 설명합니다.
3. 장바구니 물가, 예금, 대출 등 가계에 미치는 영향을 예시로 보여 줍니다.

[출력 형식]
- 형식: 정의 1문단 + 원인 번호 목록 + 생활 속 영향 목록
- 분량: 600자 내외
- 톤: 존댓말, 차분하고 이해하기 쉬운 어조
- 반드시 포함: 실생활 예시 2개 이상, 디플레이션과의 차이 한 줄

@@@ sum_0004 | 요약 | L1 | 비즈니스·마케팅 | 직장인 | 반말
>>> INPUT
이거 요약 좀

[주간 마케팅 회의]
- 9월 신규 가입자 1.2만 명, 목표 대비 85%
- 인스타 광고 CPA 상승(전월 대비 +30%), 원인은 경쟁사 광고 집행 증가로 추정
- 다음 주까지 지민: 유튜브 광고 테스트안 작성 / 현우: 쿠폰 미사용자 리마인드 푸시 기획
>>> OUTPUT
[과제 유형] 요약

[역할]
당신은 마케팅팀 회의록을 정리해 온 마케팅 운영 매니저입니다.

[과제]
아래 주간 마케팅 회의 메모를 팀원 공유용으로 요약해 주세요.

[맥락 및 가정]
- 가정: 회의에 참석하지 못한 팀원과 상사가 읽습니다.

[원문]
[주간 마케팅 회의]
- 9월 신규 가입자 1.2만 명, 목표 대비 85%
- 인스타 광고 CPA 상승(전월 대비 +30%), 원인은 경쟁사 광고 집행 증가로 추정
- 다음 주까지 지민: 유튜브 광고 테스트안 작성 / 현우: 쿠폰 미사용자 리마인드 푸시 기획

[수행 단계]
1. 성과 지표를 정리합니다.
2. 문제점과 추정 원인을 정리합니다.
3. 담당자별 액션 아이템을 정리합니다.

[출력 형식]
- 형식: '현황 / 이슈 / 할 일(담당자·기한)' 3개 항목
- 분량: 6줄 이내
- 톤: 간결한 업무 개조식
- 반드시 포함: 모든 수치, 담당자 이름, 추정 원인은 '추정'으로 표시

@@@ exp_0322 | 설명 | L3 | IT·개발 | 개발자 | 반말
>>> INPUT
팀 위키에 올릴 Kafka 소개 글 써줘. 독자는 메시지 큐 써본 적 없는 백엔드 개발자고, topic/partition/consumer group 개념이랑 RabbitMQ와의 차이까지만. 코드 예시는 필요 없고 1000자 이내로.
>>> OUTPUT
[과제 유형] 설명

[역할]
당신은 사내 이벤트 스트리밍 플랫폼을 운영해 온 데이터 플랫폼 엔지니어입니다.

[과제]
팀 위키에 올릴 Apache Kafka 소개 글을 작성해 주세요.

[맥락 및 가정]
- 용도: 팀 위키
- 독자: 메시지 큐를 써 본 적 없는 백엔드 개발자
- 범위: topic, partition, consumer group 개념과 RabbitMQ와의 차이까지
- 제외: 코드 예시

[수행 단계]
1. Kafka가 해결하는 문제를 한 문단으로 설명합니다.
2. topic, partition, offset, consumer group 개념을 순서대로 설명합니다.
3. RabbitMQ와의 차이를 설계 철학과 사용 사례 중심으로 비교합니다.

[출력 형식]
- 형식: 소제목 3개 + 비교 표 1개
- 분량: 1,000자 이내
- 톤: 위키 문서 스타일, 기술 용어는 영어 그대로
- 반드시 포함: partition과 순서 보장의 관계, 비교 표
```

## 6. 작업 방식

- 배정받은 파일만 새로 만든다. 다른 파일은 수정·삭제하지 않는다.
- 파일 하나에 20~30개씩 Write로 작성.
- 파일을 하나 쓸 때마다 검증: `python scripts/build_dataset.py --quiet` (작업 폴더에서 실행). 전체 파일을 검사하므로, **자기 파일에서 나온 오류만** 고친다. 다른 에이전트 파일의 오류나 중복 보고는 무시.
- 끝나면 만든 파일 목록, task×level별 개수, 남은 오류 유무만 짧게 보고.
